# Menkerud Home – design document

Kids' touchscreen dashboard for a family home in Raufoss, Norway. The children cannot read yet, so the main screen is three giant picture buttons (call mor, call far, "I'm home") and a sticky-note board with emoji. Parents configure everything behind a PIN. Norwegian UI (bokmål), English code and docs.

Status: v0.4, **in daily use on the kiosk** (an Asus Vivo AIO touchscreen running Google Chrome in kiosk mode) since 2026-09-10. **One-tap video calls run on LiveKit** through the `call-backend/` service on Unraid (§11) and work end-to-end; call quality is limited by the kiosk's 2-core Celeron, not by the software. The front page is a scenic background with glass panels: three call cards, then **I DAG** (today's timed notes and events) · **HUSK** (sticky notes) · **BESKJEDER** (a Discord channel read aloud). Since 2026-09-12 the body is a swipe strip of pages – Hjem · Lapper og lister · Huset · Lys · Kamera – fed by Home Assistant (§3.19, §4); since 2026-10-15 a Home Assistant **Handleliste** shows on the photo frame and on the Lapper og lister page (§3.6a). **Skjerm av**, **Bilderamme** and **Hent oppdatering** run through the kiosk screen helper. The art pack lives in `assets/`. Everything in this document is implemented unless listed under *Backlog*.

## 2. Runtime model

One page of static files, shown on a Linux desktop PC (Ubuntu) with a touchscreen, webcam and mic. In production a **local nginx serves it and Google Chrome opens `http://localhost`** in kiosk mode (SETUP.md §3); it also still works opened straight from `file://`. Non-negotiable constraints on wherever it is served:

- The origin must be a **secure context** so `getUserMedia` (the LiveKit call) works. `http://localhost`, `https://` and `file://` all qualify; **`http://<LAN-IP>` does not** and would silently lose camera/mic — never serve the screen on the LAN IP over plain http.
- The page must not be subject to **mixed-content blocking** of the `ws://` link to Home Assistant on the LAN. An `http://localhost` page (or `file://`) is fine; a `https://` page would need Home Assistant over `wss://`.
- **Skjerm av** and **Hent oppdatering** rely on the kiosk screen helper (`scripts/kiosk-screen.py`, a local HTTP shim at `cfg.screen.helper` that talks D-Bus and runs `git pull`); without it the page only shows the black overlay and updates need a shell. GNOME's own blanking stays off. **Bilderamme** relies on an nginx folder listing of `photos/` or a hand-written `photos/index.json`.
- nginx serves static files only — **no server-side logic**, and the page keeps working with nothing configured (clock/notes/night mode offline). Serving from localhost also keeps `config.js` and its token off the network.

The page must keep working with *nothing* configured (first run shows sample notes, live weather for the default place, and a friendly "not set up" message when calling). Every external dependency degrades gracefully.

### Configuration layering

```
DEFAULTS (in index.html)  ←  window.MENKERUD_CONFIG (config.js)  ←  localStorage "menkerud.settings"
```

`cfg = deepMerge(deepMerge(DEFAULTS, MENKERUD_CONFIG), SAVED)`. Objects merge recursively, arrays replace. `localStorage` access is wrapped in `store` with an in-memory fallback (sandboxed previews throw on `localStorage`). Saving settings writes only the keys the settings form manages (plus photos and weather lat/lon) and then reloads the page; there is no live re-config.

Storage keys: `menkerud.settings` (object), `menkerud.messages` (the last 10 Beskjeder `{id, who, name, text, ts, heard, read}`), `menkerud.notes` (array of `{uid, summary}`, seeded with 5 sample notes on first run), `menkerud.calendar` (array of `{uid, date 'YYYY-MM-DD', time?, icon, text, repeat 'none'|'daily'|'weekly'|'weekdays'}`, empty on first run).

### Full config schema

```js
{
  home:    { name, subtitle, tagline /* "\n" = line break */, footer,
             homeSub /* line under "Jeg er hjemme" */, background /* 'auto'|'day'|'evening'|'night'|'none' */ },
  weather: { place, lat, lon },                       // Open-Meteo; "Slå opp" geocodes place → lat/lon
  people:  { mor: { name, photo /* path or data URL, "" = none */, emoji /* fallback */, callSub /* line under "Ring mor" */ }, far: {…} },
  call:    { backend /* '' = same-origin /api via nginx; or a full URL */, deviceKey /* optional shared secret */, timeoutSec },
  notify: {
    provider: 'discord' | 'ntfy' | 'ha' | 'webhook' | 'none',
    discord: { webhook, userMor, userFar, botToken, ringChannel, msgChannel /* the Beskjeder channel */ },
    ntfy:    { server, topicMor, topicFar, topicKiosk, token },
    webhook: { url }
  },
  ha: { url, token, weatherEntity, todoEntity, ttsEntity /* "" = auto: first weather.* / todo.* (not the shopping list) / tts.* */, shopEntity /* the shopping list; "" = the todo.* named «Handle…» */, personMor, personFar /* person.* for presence; "" = match by name */,
        ttsLanguage, includeSwitches, scripts: { mor, far, home }, callEvent },
  pin,                                                // string of digits, "" = no PIN
  night: { enabled, from, to },                       // "HH:MM" – dim overlay
  screen: { offEnabled, offFrom, offTo, helper },     // "HH:MM" window + the kiosk screen helper URL (http://127.0.0.1:7777); ⏻ button any time
  pages:   { lister, huset, lys, kamera /* booleans */, homeAfterSec }, // the extra swipe pages (need HA) and the idle return to Hjem
  house:   { entities: [ 'binary_sensor.x', … ] },    // tiles on the Huset page
  messages: { autoSpeak },                            // Beskjeder: false (default) = chime + badges, someone taps to hear; true = the sheet opens and reads it as it arrives
  rooms:   [ { id, name, icon, lights: [ids], kids: [ids] } ], // Lys page: rooms, and which lights the children may toggle without the PIN
  photos: { dir, intervalSec, idleMin, shopList },    // shopList = the shopping-list card on the frame (default true). Bilderamme: 'photos/', '/bilder/' (nginx alias of a mounted share) or a CORS-enabled http:// folder; subfolders included. idleMin = start by itself after n minutes without a touch (0 = never)
  emojis: [ … ]                                       // picker under Ny lapp
}
```

Person keys are `mor` / `far` throughout (`cfg.people`, `data-who`, `data-name`, card ids `#card-mor`, CSS classes `.mor`/`.far`, push targets). Display names come from `cfg.people.X.name`; never hard-code "Mor"/"Far" in UI strings.

### Layout system

`html { font-size: min(1vw, 1.7778vh) }` → **1rem = 1 % of screen width on a 16:9 screen**, so every size in the CSS is in `rem` and the whole layout scales to any resolution. `body` is a 3-row grid (header / **`#pages`** `1fr` / footer) locked to `100vh`, `overflow: hidden`. `#pages` clips a horizontal flex **strip** of full-size `.page`s; the first, `.page.home`, is itself a 2-row grid (cards `1.02fr` / **bottom-grid** `1fr`) – the layout the kids see – and the others (Huset, Lys, Kamera) are plain grids over the scenic background. The bottom row is a three-column grid — **I DAG · HUSK… · BESKJEDER** (`.bottom-grid`, `~1 / 2 / 1`); when Beskjeder is not set up (no bot token or message channel) its column is removed and the grid falls back to two columns (`.no-messages`). A fixed scenic photo sits behind everything (`#bg`, set by `pickBackground`) over a CSS aurora/gradient fallback, under a legibility gradient. The primary target is 1920×1080 landscape (design canvas); narrower landscape sizes only tighten spacing. Portrait shows a "snu skjermen" message rather than reflowing. Fonts: Nunito (UI) and Caveat (handwriting: tagline, notes, footer) from Google Fonts with system fallbacks; emoji rely on the OS emoji font (`fonts-noto-color-emoji` on Linux).

## 3. Module map (order inside the IIFE in `index.html`)

1. **Defaults & storage** – `DEFAULTS`, `SAMPLE_NOTES`, `deepMerge`, `getPath`/`setPath`, `store`, `cfg`, `haOn`, `toast`, overlay helpers, `setAvatar`.
2. **`class HA`** – minimal Home Assistant WebSocket client: auth, incrementing ids, `send`, `subscribe`, `callService`, ping every 30 s, reconnect with backoff. `ha.onready` fetches `get_states`, picks entities, subscribes to `state_changed`, `todo/item/subscribe`, and the custom call event.
3. **Clock / weather / night / background** – `tick` (nb-NO locale; re-renders the schedule on the minute), `renderWeather` (HA entity wins, else Open-Meteo `wxOpen`), `fetchOpenMeteo` every 15 min, `geocode`, night overlay (`nightMode` auto/on/off, `awakeUntil`, never while an overlay is open), `pickBackground` swaps the scenic background by clock or `home.background`. **Screen off:** `checkNight` also derives `dark` (`restMode`, set by the ⏻ header button, or the `cfg.screen` window via `inScreenOff`/`inWindow`) → `#night.dark` (solid black) and, on every change of `dark`, `screenPower(!dark)` → `GET <cfg.screen.helper>/off|/on` (`mode: 'no-cors'`, fire-and-forget) to the kiosk screen helper, which sets the backlight to 0 through logind (the panel and touch controller stay powered) and restores it on the first touch; a touch on `#night` clears `restMode`, buys two minutes (`awakeUntil`) and thereby asks for the display back; an incoming call (`showOverlay`) does the same, so the screen lights up for it. **Bilderamme:** `startFrame` → `listPhotos` (`<cfg.photos.dir>/index.json`, else `listDir` walks the folder and its subfolders through nginx autoindex – JSON or HTML – capped at 4 levels / 150 folders / 2000 pictures, `junkName` skips hidden and share clutter; `dir` is `photos/`, a same-origin path such as `/bilder/` that nginx aliases to a mounted network share, or a CORS-enabled `http://` folder elsewhere) → shuffled slides in `#frame` (`showSlide`: blurred backdrop + `object-fit: contain` image, 1.2 s crossfade every `intervalSec`, broken files skipped); any touch → `stopFrame` (+2 min awake); `showOverlay` (incoming call) and Escape stop it too. A frame started by hand keeps the wake lock and ignores the night window. **Idle start:** `checkIdleFrame` (from `tick`) starts the frame by itself (`startFrame(true)`, `frameAuto`) after `cfg.photos.idleMin` minutes without a `pointerdown`/`keydown` (`lastInput`), never while an overlay is open, ⏻ is pressed or the screen-off window is on; one attempt per idle period (`idleFrameTried`) so an empty folder toasts once. `checkNight` stops an auto-started frame when the screen-off window begins, so the display still goes dark.
4. **Sound** – WebAudio only: `ring` (425 Hz, 1 s on / 4 s off = Norwegian ringback), `chime` (C-E-G).
5. **`speak(text)`** – HA TTS via `media_source/resolve_media` → `<audio>`; fallback `speechSynthesis` `nb-NO`.
6. **Notes** – `localNotes` vs `haNotes`, `notesSource()`, `parseNote` (leading emoji cluster via `\p{Extended_Pictographic}`, optional `HH:MM`), `spokenTime` (klokka fem / kvart over / halv / kvart på, 12-hour), `renderNotes`, `addNote`, `removeNote`. The board shows the **newest `NOTES_ON_BOARD` = 5** notes side by side (8.4 rem wide, no side-scrolling) and a «+N flere ›» pill in the title when there are more; the pill or the panel opens the **Husk sheet** (`#notesheet`, `renderNoteSheet`: every note, 5 per row, tap = wiggle + speak). `noteEl` builds a note for both places. Sheets share `openSheet` / `touchSheet` / `closeSheet` / `closeSheets` (`.overlay.sheet-wrap`, idle auto-close, any other overlay closes them). `renderSchedule` merges the notes that carry a time **and today's calendar events** into the **I DAG** panel (all-day events first, then by time; past ones dimmed, one highlighted when near now) with a 06:00→21:00 day-progress bar. The **Kalender** pane (`renderCalendar`, `eventsOn`/`occursOn`, `addEvent`/`removeEvent`) is a month grid you tap to add dated events with an optional time and a simple repeat (daily / weekly / weekdays), stored in `menkerud.calendar`; it reuses the emoji picker, time stepper and docked keyboard.
6a. **Handleliste** (2026-10-15) – a second HA to-do list, `shopId` = `cfg.ha.shopEntity` or `findShopEntity()` (the `todo.*` whose id or friendly name contains «handle»); the notes board's auto-pick (`todoId`) skips it. `ha.onready` subscribes with `todo/item/subscribe` → `shopItems` (all items, `status` `needs_action` / `completed`) → `renderShop()`, which paints three places: the **frame cart** `#frame-shop` (a round 🛒 button top-left over the photos with the open count in a yellow bubble, no item names; hidden when the list is empty, HA is down or `cfg.photos.shopList` is false; a solid tint instead of `backdrop-filter` to spare the kiosk CPU during the crossfade), the **sheet** `#shopsheet` (`openShopSheet`; tapping the cart opens it *on top of the running slideshow*: `openSheet(sel, ms, keepFrame)` skips `stopFrame` and marks the sheet `.on-frame` – a light dim without `backdrop-filter`, so the crossfade stays cheap – and closing it, by hand or by the 60 s timeout, goes back to the pictures; `stopFrame` drops `.on-frame`) and the **Lapper og lister** page (`renderListerShop`). `shopRowsHTML` lists open items first and bought ones under «KJØPT»; a tap on a row → `toggleShopItem` → status flipped locally at once, then `todo.update_item {item: uid, status}` (rolled back with a toast on failure; the subscription confirms). «Fjern kjøpte» in the sheet → `todo.remove_completed_items`. A **Handleliste** status card shows the entity and the open count.
7. **`sendPush(target, kind)`** – `target` = `'mor' | 'far' | 'both'`, `kind` = `'call' | 'again' | 'home' | 'test'`. Branches per provider. Throws with a Norwegian message on failure; callers toast it.
8. **Incoming listeners** – `listenNtfy` (WebSocket `/<topic>/ws`), `listenDiscord` (gateway) and `listenBackend` (the call-backend's event stream, §5). All three reconnect with backoff, update `ntfyState` / `dcState` / `beState` for the status panel, and may run at once. `listenBackend` (2026-11-14; **the backend side is not deployed yet** – until part 3 of the parent-app work the production backend answers this address with 404 and the kiosk just keeps asking quietly) holds one `GET <cfg.call.backend>/api/kiosk/events` open and hands every event to `onBackendEvent`: `incoming` → `incomingCall(from, callId)` and a `POST …/api/calls/<id>/ringing` that tells the backend the call is ringing on the screen (without it the backend counts the screen as not connected after 8 s), or an immediate decline when the kiosk is busy; an `incoming` for the call that is being answered right now (the backend repeats a ringing call to a stream that reconnects) is ignored; `cancelled` / `ended` → the incoming overlay closes quietly; `declined` / `ended` on a call from here → `couldNotAnswer` (§3.10). It never shows anything itself: a stream that will not open is tried again after 2 s, growing ×1.5 to a minute; 45 s without a byte (the API writes a keep-alive every 20 s) counts as a dead line; a refused device key (401 / 403 → `beState = 'denied'`) is tried again only every five minutes. While the stream is open the «… ringer hjem» status card reads «Appen ✓», followed by the older listener's text when one of those is on too.
9. **`imHome`** – chime, confetti, overlay, TTS, push to both.
10. **Calls (LiveKit)** – `startCall(who)` → `startCallLiveKit`: `showCalling` opens the overlay, the kiosk POSTs `cfg.call.backend`/`api/calls` (with `X-Device-Key` if set) and hands the answer to `connectCall(who, callId, livekit)` – the LiveKit part, shared by both directions: `loadLiveKit` lazy-loads `livekit-client` from a CDN, the kiosk joins the room, sends camera and microphone, attaches the parent’s remote video into `#callvideo` and hides the calling layer; `endCall` disconnects and POSTs `…/end`. Every attempt has a number (`callSeq`, also bumped by `endCall`): an answer from the API that arrives after the child has hung up – or has already pressed the other parent – finds that it is no longer the attempt on screen, ends its call on the server and touches nothing. `incomingCall(who, callId)` / `dismissIncoming(tellBackend)` handle "parent rings home". Without a `callId` (ntfy, Discord, the HA event) **Svar** calls the parent back, as always. With one (the parent rang from the app – `listenBackend`, §3.8; **built 2026-11-14; waits for the new backend**) **Svar** → `joinCall(who, callId)`: `POST …/api/calls/<id>/answer` with the device key (`callApi`), then `connectCall` into the room where the parent already waits; **Ikke nå** or the 45 s timeout → `POST …/api/calls/<id>/decline`, so the parent's app stops waiting. Every closing message («… kunne ikke svare nå», «Bildet … kom ikke fram», «Klarte ikke å starte samtalen», «Kunne ikke laste videosamtalen») goes through `closeCall(text, ms)`, which sets `callOver` until the hang-up so that later news about the same call neither replaces the message nor cuts it short. `couldNotAnswer(who)` is the one place that says «… kunne ikke svare nå»: the kiosk's own ring time, «Ikke nå» in the app (`declined`), the server giving up (`ended`) and the room closing under a call that still rings all end there, and only the first one speaks. A parent or a picture arriving during a closing message still gets through (`awaitPicture` and `TrackSubscribed` clear `callOver`). A call answered here (`callJoined`) or one with the picture showing just closes when the room does. Room events from a room the kiosk has already left are ignored (`lkRoom !== room`), and a «disconnected» before the kiosk is in the room is only the connect failing – the catch says «Klarte ikke å starte samtalen».
11. **Confetti** – canvas, 3.8 s.
12. **PIN** – `gate(fn)` runs `fn` after a correct PIN (`pinNext`; no PIN configured = at once); `openMenuGate` = `gate(openMenu)`, the Lys page uses it for locked lights.
13. **Menu** – the parents' area is one near-full-screen glass sheet (`#menu` → `.panel`, the scene blurred behind it): a section list on the left (`#menu-nav`, `.nav-item[data-pane]`, one accent colour per section, and a live one-line status under each name from `navSubs()`/`renderNav()` – notes on the board, today's plans, lights on / cameras found, or «Via Home Assistant» when HA is not configured) and the open section on the right (`.panel-main`: handwritten title, ✕, `.panel-body`, the docked keyboard). `showPane(name)` for `note | calendar | lights | cams | settings`; `openMenu` lands on Ny lapp. There is no launcher grid and no back button – every section is one tap from every other. `renderNoteList`, `renderCalendar`, `renderLights` and `renderCams` call `renderNav()` so the counts stay live.
14. **On-screen keyboard** – docked at the bottom of the panel, attaches to any focused `input.inp` inside `#panel` (`focusin`), `abc`/`sym` layouts, shift, caret-aware insert via `setRangeText`, dispatches `input` events so bindings update. `data-num="1"` inputs open in the symbol layout.
15. **Lights / cameras / Beskjeder** – all `light.*` (+ `switch.*` if configured) as tiles → `homeassistant.toggle`; cameras via MJPEG `/api/camera_proxy_stream/<id>?token=<access_token>`. **Beskjeder** (replaced the KVELD panel on 2026-09-13; `messages`, key `menkerud.messages`, `MSG_KEEP = 10`): `listenDiscord` routes gateway events in `notify.discord.msgChannel` to `onNewMessage` / `updateMessage` / `removeMessage`; on READY `fetchMessageHistory` pulls the channel's last 10 through the call-backend (`backendApi`; see §5 Discord for why not directly) (new ones wait as unread, local copies missing from the list are dropped = deleted while the kiosk was off). `renderMessages` paints the front-page panel (3 rows, unread badge; hidden and `.bottom-grid.no-messages` when there is no bot token or channel) and `renderMsgSheet` the full-screen `#msgsheet`: numbered rows, `.mplay` → `speakMessage` (sets `heard`, unlocks the button), `.confirm` «✅ Hørt!» → `confirmMessage` (sets `read`, `ackMessage` has the backend put a ✅ reaction, `postConfirmation` posts «@Mor ✅ Beskjeden er hørt (HH:MM): «…»» through the #hjemme webhook). `onNewMessage`: badge on the panel **and on the photo frame** (`#frame-msgs`, tap → the sheet) plus a chime – unless `quietHours()` (night overlay, screen-off window, ⏻) or a call is on, then silently. Only with `cfg.messages.autoSpeak` (off by default: nobody may be home yet) does it also wake the screen, open the sheet and read the message. The badges count messages not yet confirmed. Any other overlay (`showOverlay`) closes the sheet; it also closes itself after 30 s (auto-opened) / 60 s (opened by hand) without a tap.
16. **Settings** – tabbed. A **Status** tab (`renderStatus`: 10 status cards (one is **Handleliste**) with a green / red / amber / grey dot – the last one, **Versjon**, is the commit the helper reports via `fetchVersion` → `GET <helper>/version` – then the test buttons and **⬇️ Hent oppdatering** → `updateApp` → `POST <helper>/update` → toast «Oppdatert a → b» and reload, or «Allerede oppdatert») plus one tab per `{ tab, l, intro? }` entry in the `SETTINGS` schema array (Familie · Samtale · Home Assistant · Skjerm · Bilderamme; `{ sec }` entries are headings inside a tab). `buildForm(keepDraft)` renders every tab into `#settings-form` as `.sgroup[data-tab]` and `renderSettingsTabs()` shows the active one (`settingsTab`; a fresh open starts on Status, the rebuild after a provider change stays put). `draft` object → `saveSettings` → reload; the Lagre / Nullstill row is pinned to the bottom of the pane and hidden on the Status tab. Field kinds: text (`k`), `num` (numeric keyboard), `number` (coerced on save), `select`, `toggle`, `photo`, `geocode`, `show: '<provider>'` to hide unless that provider is selected.
17. **Ny lapp form** – emoji strip, time stepper, text input, live preview note, chip list with delete.
18. **`init()`** – applies texts/avatars, binds events, starts clock, weather, HA (if configured) and the three listeners (§3.8).
19. **Pages** – `PAGE_DEFS` → `buildPages()` keeps only Hjem unless HA is connected and the page is on in `cfg.pages`; `goPage(i)` translates `#strip`, paints the footer dots/arrows (`#page-nav`, hidden with one page) and renders the page that came into view. **Lapper og lister** (`lister`, second in the strip): every note as a sticky note (`renderListerNotes`, reuses `noteEl`, tap = read aloud; `renderNotes` refreshes it while visible) beside the Handleliste (§3.6a). Swipe = `swipeStart/Move/End` on `#pages` (pointer events; capture only after a clear sideways move, so taps stay taps; the click after a swipe is swallowed once; `.notes` keeps its own horizontal scroll via `touch-action`). `checkIdlePage` (from `tick`) slides back to Hjem after `pages.homeAfterSec` without a touch. **Presence:** `personEntity(who)` = `cfg.ha.personMor/Far` or a `person.*` whose friendly name matches `cfg.people.X.name`; `presenceOf` → home / away / zone / unknown; `renderPresence` paints the `.pres` badge on the call cards and the **Huset** page's who-tiles. **Huset:** `renderHouseTiles` renders `cfg.house.entities` through `tileFor(id)` (icon + Norwegian text per domain / device_class; `alert` for open doors, unlocked locks, leaks …). **Lys:** `renderRooms` groups `light.*` (+ `switch.*` if `ha.includeSwitches`) by `cfg.rooms`, unassigned ones under «Andre lys»; lights in a room's `kids` list toggle at once, the rest go through `gate()` (PIN) which then frees every light for two minutes (`parentUntil`). **Kamera:** snapshots via `/api/camera_proxy/` every 10 s while the page is visible, tap → `/api/camera_proxy_stream/`; `camPageHide` drops all `src`s. **Settings → Sider:** page toggles, `kind: 'entity'` pickers (a `<select>` of one domain from `ha.states`, also used for the weather/todo/tts entities), `kind: 'entities'` chip set for the house tiles, and the `roomsEditor` (`kind: 'rooms'`: name via the docked keyboard, icon, and per light «I rommet» / «Barna kan styre»).

**To add a setting:** add a default in `DEFAULTS`, one entry in `SETTINGS` under the right `{ tab }` (it renders, drafts and persists automatically), and read it from `cfg` where needed. Add a status row in `renderStatus` if it has a connection state. Update the smoke test's "form rows" count if you assert on it.

## 4. Flows

**Kid presses "Ring mor"** → `startCallLiveKit('mor')` → overlay with photo + "Ringer mor…", ring tone, TTS "Ringer Mor" → `POST cfg.call.backend/api/calls {target:'mor'}` (the backend DMs the parent an **Svar** link) → connect to the returned LiveKit room; on `ParticipantConnected` the ring tone stops and the status says «Mor er med – venter på bildet…»; on the parent’s `TrackSubscribed` the remote video fills `#callvideo` and the calling layer hides → after `call.timeoutSec` still ringing with nobody joined: "Mor kunne ikke svare nå" and hang up; joined but no video for 20 s: «Bildet fra mor kom ikke fram 😕 Prøv igjen» and hang up (the phone refused camera/mic – typically Discord's in-app browser, found 2026-09-15). The answer page detects in-app browsers (`; wv)` in the UA) and shows «🌐 Åpne i Chrome» (an Android `intent://` link to Chrome) before joining, keeps a camera/mic refusal on top of the incoming video with «Prøv igjen» + «Åpne i Chrome», and the DM itself says to open the link in Chrome. Big red "Legg på" always visible → `endCall` disconnects and tells the backend.

## 5. External protocols (exact)

**LiveKit** – the kiosk connects with `livekit-client` (`new Room(...)`, `room.connect(url, token)`, `localParticipant.enableCameraAndMicrophone()`, `RoomEvent.TrackSubscribed`/`Disconnected`). Rooms, participant tokens and the Discord answer-link DM are the backend’s job (`call-backend/`, `livekit-server-sdk`); the kiosk never holds the API secret. Signaling is WSS through SWAG (`rtc.`); media is a single UDP port (7882): devices at home reach LiveKit on its LAN address (`192.168.68.2`), everything else on the home's public IP. LiveKit advertises both (`rtc.advertise_internal_ip`, DEPLOYMENT.md §2) because the routers do not hairpin.

**Call-backend event stream** (built 2026-11-14/15; **the backend side is not deployed yet**) – `GET <cfg.call.backend>/api/kiosk/events` with `X-Device-Key`, answered as `text/event-stream` and held open. Read with `fetch` + `body.getReader()` + `TextDecoder`, because `EventSource` cannot send the header. Frames are `data: <json>\n\n`: `{type:"hello"}` on connect, `{type:"incoming", callId, from, expiresAt}`, `{type:"cancelled", callId}`, `{type:"declined", callId}`, `{type:"ended", callId}`; a comment line `: ka` every 20 s keeps proxies from closing an idle stream and lets the kiosk notice a dead one (45 s of silence → reconnect). Types the kiosk does not know are ignored. A stream that connects while a parent's call is ringing gets that `incoming` again right after `hello`. For an `incoming` it shows, the kiosk at once sends `POST …/api/calls/<callId>/ringing` → `{status}` – a call the backend hears nothing about for 8 s ends as `unreachable` – and then `POST …/api/calls/<callId>/answer` → `{callId, livekit: {url, token}}` or `POST …/api/calls/<callId>/decline` → `{status: "declined"}`; all three with `X-Device-Key` and a `{}` body. 401 / 403 on the stream means the API refuses the device key (403 `device_key_required`: the server has none, and then these kiosk routes are closed altogether); the kiosk asks again every five minutes. Everything else is retried after 2 s, growing ×1.5 to a minute. Until the new backend is deployed the old one answers this address with 404, which the kiosk treats like any unreachable stream: quietly, at most one try a minute. The full API contract, including what the parent app sees, is in `docs/superpowers/plans/2026-11-14-parent-app-1-api-and-kiosk.md` (C1–C11).

**ntfy** – publish: `POST <server>/` with JSON body `{topic, title, message, priority (5 = max), click, actions:[{action:'view', label, url, clear:true}]}`; optional `Authorization: Bearer tk_…`. Sent as a plain string body (no Content-Type) so the request is CORS-simple. Subscribe: `WebSocket <server ws(s)>/<topic>/ws`, optional `?auth=<base64('Bearer tk_…') without '='>`; messages are JSON lines with `event: 'open' | 'keepalive' | 'message'`. A message whose text contains `mor`/`far` (word) or the legacy `mamma`/`pappa` rings the kiosk as that parent.

**Discord** – outgoing via **webhook**: `POST <webhook url>` JSON `{content, username}`; `content` starts with `<@userId>` mentions (or `@here` if no ids) so phones get notified under "only @mentions". Incoming via **gateway**: `wss://gateway.discord.gg/?v=10&encoding=json`; op 10 Hello → start heartbeat (op 1 with last `s`) and send op 2 Identify `{token, intents: 513 /* GUILDS | GUILD_MESSAGES */ | 32768 /* MESSAGE_CONTENT, only when msgChannel is set */, properties}`; op 11 = ack (missing ack → close/reconnect); op 7/9 → reconnect; `t: 'READY'` → state on; `t: 'MESSAGE_CREATE'` in `ringChannel` from a non-bot, non-webhook author → `incomingCall(author.id === userFar ? 'far' : 'mor')`. Ringing reads no content, so any human message in that channel rings. **Beskjeder** need the privileged MESSAGE_CONTENT intent (Developer Portal → Bot → Privileged Gateway Intents); if the bot is not allowed it the gateway closes with **4014**, the kiosk sets `dcNoContent`, re-identifies with 513 after 0.5 s and the Beskjeder status card says what to enable. `t: 'MESSAGE_CREATE' | 'MESSAGE_UPDATE' | 'MESSAGE_DELETE'` in `msgChannel` maintain the list. The two REST calls do **not** go to Discord from the page: Discord answers 403 `{"code": 40333}` to any bot token that arrives with a browser User-Agent, and that answer has no CORS headers, so the page only sees «Failed to fetch» (verified 2026-09-13). They go to the **call-backend** instead – `GET <cfg.call.backend>/api/messages?channel=<msgChannel>&limit=10` on READY and `POST …/api/messages/<msgChannel>/<id>/ack` on «Hørt!», with `X-Device-Key` when one is set (`backendApi`) – and the backend calls Discord with its own `DISCORD_BOT_TOKEN` (`GET /channels/:id/messages`, `PUT …/reactions/%E2%9C%85/@me`; it needs Read Message History + Add Reactions in the channel). The confirmation line still goes straight to the webhook, which Discord allows from browsers. A bot token may have several concurrent sessions, so the parents' existing bot can be reused.

**Home Assistant WebSocket** – `/api/websocket`: `auth`, `get_states`, `subscribe_events {event_type}`, `todo/item/subscribe {entity_id}` (events carry `{items:[{uid, summary, status, description?}]}`; one subscription for the notes list, one for the shopping list), `call_service {domain, service, service_data, target}` (`todo.add_item {item}`, `todo.remove_item {item: uid}`, `todo.update_item {item: uid, status: 'completed'|'needs_action'}`, `todo.remove_completed_items`, `script.turn_on`, `homeassistant.toggle`, `light.turn_off`), `media_source/resolve_media {media_content_id: 'media-source://tts/<tts entity>?message=…&language=no'}` → `{url}` (relative `/api/tts_proxy/…`, unauthenticated). Camera MJPEG uses the entity's `access_token` attribute.

**Open-Meteo** – `https://api.open-meteo.com/v1/forecast?latitude&longitude&current=temperature_2m,weather_code,is_day&timezone=auto`; geocoding `https://geocoding-api.open-meteo.com/v1/search?name&count=1&language=no&format=json`. WMO code → emoji in `wmoIcon`.

## 6. Conventions

- Vanilla JS, no framework, no build. Keep it one file; the kiosk deploys with a `git pull` of static files (§4 «Hent oppdatering»).
- All user-visible text is Norwegian bokmål, sentence case, plain verbs. Kids never need to read: anything the child must act on is a picture or a colour (green = yes, red = stop).
- Escape everything dynamic with `esc()`. Never `innerHTML` raw user data.
- Every network feature must fail into a toast or a status row, never into a broken screen. Offline = clock, notes, night mode still work.
- Sizes in `rem` only (see layout system). Touch targets ≥ 3 rem. `button` elements for anything tappable.
- Motion: one ambient animation (aurora drift, disabled under `prefers-reduced-motion`); everything else answers a tap.
- Names/ids: `mor`/`far` internal keys; `cfg` is the single source of truth after load; settings changes reload the page.
- Secrets (HA token, Discord bot token) are stored in plain text in `localStorage`/`config.js` on a LAN-only device. Never host the folder publicly. Say so in docs if you add new secrets.

- Full-screen layers that go away on a touch (`#night`, `#frame`) act on `click`, never on `pointerdown`: hiding a layer on the touch-down lets the pointerup/click of that same tap fall through to the card underneath – on the kiosk that placed a call at night.

## 8. Decisions and why

- **Standalone page, not a Lovelace dashboard**: HA became optional, and a Lovelace dashboard could not host the call UI with camera access (originally the Jitsi iframe, now the LiveKit client).
- **Jitsi, self-hosted on Unraid** *(historical; replaced by LiveKit on 2026-09-10, §11)*: browser-only video, IFrame API join/leave events for the "ringing" UX. The Jitsi UX still required joining a meeting, which is wrong for a child.
- **Discord default for notifications**: the family already uses it, zero new apps, and the channel doubles as a log. Known limit: cannot ring through a phone on silent/DND. ntfy kept as the alternative that can (priority 5).
- **Discord bot in the page** instead of a server-side bot: keeps the screen to static files; the token is on a LAN device only. The gateway (ringing, Beskjeder) still runs in the page; only the two REST calls Discord refuses from browsers go through the call-backend (§5).
- **Settings in `localStorage`** with `config.js` defaults: parents can set up everything on the touchscreen; tokens can be pre-seeded in the file.
- **Local notes fallback**: the board must work without HA; HA to-do list wins when present so parents can add from phones.
- **`rem` = 1 % width**: one number system for a fixed-aspect screen, no media-query soup.

- **The parents' menu is a sidebar sheet, not a launcher grid (2026-09-11).** The first version was a centred panel with a 5-tile «Meny» grid, a back button and one long settings scroll – it worked but looked nothing like the front page. Now it is one glass sheet with the scene showing through, a section list on the left (accent colour per section, live counts) and the section on the right, so every task is one tap away and the docked keyboard never pushes the navigation around. Settings got tabs per topic with Lagre pinned at the bottom instead of a 40-row scroll. The handwritten titles and the sticky-note preview tie it to the front page.

- **Screen off through a local helper, not the Wake Lock API (2026-09-10).** Chrome 153 on the kiosk's GNOME 50/Wayland session never registers an idle inhibitor for `navigator.wakeLock`, so «release the lock and let GNOME blank» failed on the real hardware. `scripts/kiosk-screen.py` sets the backlight to 0 through logind's `SetBrightness` instead: immediate, deterministic, and it can light the screen up for an incoming call. DPMS-off (Mutter `PowerSaveMode` 3) was the first version and is only the fallback now: on the Vivo AIO it powers down the USB touch controller with the panel, so no touch could ever wake the screen. It is a separate user-level process, so `index.html` stays one static file and nginx stays static-only.

## 9. Integrating with the family's existing Discord bot

The parents already run a Discord bot (its code is available alongside this repo) and the screen will live on the same server. Two ways to wire them; pick per situation, don't build both:

**A. Screen talks Discord directly (current default).** Webhook out, gateway session in with the existing bot's token. Zero changes to the bot. Fine as long as the bot doesn't already react to every message in the ring channel.

**B. The bot owns Discord, the screen talks to the bot.** Move the Discord logic into the bot and keep the screen dumb:
- Outgoing: set `notify.provider = 'webhook'` and point `notify.webhook.url` at an HTTP endpoint on the bot. The screen POSTs `{event: 'call'|'again'|'home'|'test', to: ['mor'|'far'], title, message, link}`; the bot posts to Discord however it likes (buttons, embeds, DMs, slash-command replies – things a webhook can't do). The endpoint must answer CORS (`Access-Control-Allow-Origin: *`, allow `Content-Type`) because the screen is a `file://` page.
- Incoming: the bot detects "ring hjem" (a slash command, a reaction, a message) and needs to reach the screen. Cheapest with what exists today: the bot publishes `mor`/`far` to the screen's **ntfy kiosk topic** (self-hosted ntfy or ntfy.sh) – the screen already listens there. If you'd rather not involve ntfy, add a small generic listener to the screen (SSE or WebSocket to a bot endpoint, same message shape as ntfy: `{event:'message', message:'mor'}`) as a new `notify.custom` block in `DEFAULTS` + `SETTINGS` + a `listenCustom()` next to `listenNtfy()`.

Rule of thumb: if the bot is stable and always on, B keeps the token out of the screen and gives richer Discord UX; if the bot is a hobby process that restarts a lot, A keeps calling independent of it.

There is no test for a call push that arrives on a phone that is not paired (it is asked about, answered «gone», and does not ring).
  - A camera or microphone that will not start is only shown by a red button; when it is the microphone, the screen should say so in words.

## 11. Calls: LiveKit + Discord (live since 2026-09-10)

Jitsi's UX was wrong for a child (join a meeting, type a name, pick a room), so it was replaced with a one-tap flow: tap a parent → the screen rings and joins a private LiveKit room → the parent gets a Discord message with an **Svar** link → tapping it opens a tiny answer page that joins the same room. Full spec: the LiveKit design doc supplied by the operator. The flow has worked end-to-end (video and audio both ways) since the evening of 2026-09-10.

Decisions (locked 2026-09-10):

- **Separate backend, not in `index.html`.** A small Node service — a **Docker container on Unraid** (`menkerud-callapi`, `call-backend/`, listens on 3000, host-published 3008, joined to `noobventure-network`) — owns the LiveKit API secret, the Discord bot token (reuse GameNoobBot's), the call state, one-time answer tokens and short-lived LiveKit JWTs. Since 2026-09-13 it also proxies the two Beskjeder REST calls (`GET /api/messages`, `POST /api/messages/:channel/:id/ack`), because Discord refuses bot tokens from browsers. The kiosk keeps every `CLAUDE.md` rule: one file, still works from `file://`; the LiveKit client is lazy-loaded from a CDN only during a call. The Ubuntu screen only serves static files and runs Chrome — no Node, no backend.
- **Domains** (SWAG + Cloudflare, proxied): `rtc.noobventure.com` → LiveKit `:7880` on Unraid (WSS); `call.noobventure.com` → the `menkerud-callapi` container (SWAG resolves it by name over `noobventure-network`) for the kiosk's `/api` calls and the parent answer page; `ha.noobventure.com` → Home Assistant `192.168.68.3:8123` (added 2026-09-12) so the Companion apps can post location and sensors from outside – the kiosk itself keeps the LAN URL, and HA trusts SWAG's br0 IP `192.168.68.4` as its reverse proxy (a UI setting since HA 2026.8; DEPLOYMENT.md §2). **UDP 7882** forwarded WAN → Tower for WebRTC media (two hops; see SETUP.md §2 for the double-router note).
- **Parent notification:** a private Discord **DM** from the bot with the answer link (fallback: post to `#hjemme` like today).
- **Single call engine:** LiveKit is now the only call path (`startCallLiveKit`). The Jitsi client, the `cfg.call.provider` toggle, the SWAG `meet` conf and the UDP 10000 forward were all removed on 2026-09-10.
- **Child UI reuses the redesigned call states** (idle → ringer → tilkoblet → svarte ikke) already in `index.html`; only the transport underneath changes.

**What was built:** the `call-backend/` service (Express + `livekit-server-sdk` + Discord DM over REST) with `POST /api/calls`, `/api/calls/answer`, `/api/calls/:id/cancel|end`, `GET /api/calls/:id`, the parent answer page (`public/answer.html`, `livekit-client` from CDN), `Dockerfile` + `docker-compose.yml` (the `menkerud-callapi` container on `noobventure-network`, host 3008→3000) + `livekit.example.yaml` (LiveKit reference), `deploy/nginx-menkerud.conf` (Ubuntu static site), the SWAG confs in `swag/` (`rtc.`, `call.`, and since 2026-09-12 `ha.`), plus `README.md` and the top-level **`DEPLOYMENT.md`** (source of truth for deployment). In `index.html`, `startCall(who)` → `startCallLiveKit` + `loadLiveKit` (lazy CDN); `cfg.call.backend` defaults to `https://call.noobventure.com` (a blank value would fall back to same-origin), with `cfg.call.deviceKey` / `cfg.call.timeoutSec`; Jitsi is gone. The container was deployed on Tower and the first real call went through on 2026-09-10. Later changes: the Beskjeder proxy routes (2026-09-13), the in-app-browser guard on the answer page (2026-09-15, §4) and LiveKit advertising its LAN address next to the public one (2026-11-14, §5). The parent→screen (incoming) flow over LiveKit is built for the parent app – next paragraph – but not deployed.

**Parent app, part 1 – API and kiosk (built and tested 2026-11-14/15, merged into `main` on 2026-11-15; the backend is NOT deployed).** Discord was only ever the way to the parents' phones because it was already on them; a sideloaded Android app replaces it for calls (design: `docs/superpowers/specs/2026-11-14-parent-app-design.md`, plan: `docs/superpowers/plans/2026-11-14-parent-app-1-api-and-kiosk.md`, which also holds the API contract the app is written against). Messages stay on Discord. What part 1 added:
- **The backend in pieces** – `server.js` is wiring only; `config.js`, `app.js` (routes), `calls.js`, `devices.js`, `push.js`, `kiosk-events.js`, `admin.js`. Each takes what it needs as arguments, so each has a test of its own.
- **Pairing** – the operator makes a one-time key (20 characters, valid 15 minutes, once) for Mor or Far on a **local-only page** on a second port (host 3009, never proxied by SWAG – nothing of it exists on `call.noobventure.com`), as text and as a QR code (`menkerudhome://pair?api=…&code=…`). The app redeems it at `POST /api/pair` and gets a secret; the server keeps only its SHA-256. Which parent a phone is comes from the server's record, never from a request. The phone list lives in the data folder (`/mnt/user/appdata/menkerud-callapi` on Unraid), outside the project folder that the dev PC's sync mirrors.
- **Push** – `push.js` sends data-only, high-priority messages through Firebase Cloud Messaging (HTTP v1, signed with Node's own crypto – no SDK). Per parent: at least one phone with a live push address → the call goes to the app; otherwise the Discord link exactly as before. A phone whose address is dead no longer counts.
- **Both directions** – `calls.js`: kids call a parent (`POST /api/calls`; the phone answers or declines with its secret), a parent calls home (`POST /api/calls/home`; the kiosk is told on its event stream and answers or declines with the device key). One call at a time. Nothing can hold the line: a call that is answered but never reported as ended is found by a watchdog that looks into the LiveKit room, a call's ring time runs from the moment it is made, and a call that fails while it starts is dropped. The kiosk has to confirm a parent's call within 8 s (`…/ringing`); if it does not, the call ends as `unreachable` and the app says the screen is not connected – that catches a kiosk whose network died without closing its stream.
- **The kiosk** – `listenBackend`, `joinCall`, `connectCall` and friends (§3.8, §3.10, §4, §5). Nothing on the screen changed except the text of the «… ringer hjem» status card.
- **A dev copy** – `call-backend/.env.dev.example`, `npm run dev`, `scripts/fake-phone.js` (a stand-in for the app) and `dev/join.html` (its call screen): own ports, own data folder, pushes written to a file, no Discord token (`call-backend/README.md`, «Developing on a separate copy»). On 2026-11-15 the whole of it ran on this dev copy – the real kiosk page in Chrome, the stand-in phone, the real LiveKit server: calls in both directions with picture and sound both ways, «Ikke nå» both ways, «Opptatt hjemme», the screen not connected, a phone removed while listening, and the kiosk finding its way back by itself after the backend was restarted.

**Parent app, part 2 – the Android app (built 2026-11-15 on `experimental`; NOT yet run on a phone, and nothing is paired with production).** `parent-app/` is a sideloaded Android app – Kotlin, Compose, LiveKit's Android SDK, Firebase Cloud Messaging – that is paired once with a key, rings when the kids call, joins the call on «Svar», and can ring home. Everything that *decides* something (reading a key, the API, reading a push, the life of a call, pairing, «is the phone ready») is plain Kotlin with a test on the PC: 115 tests, and 7 more that run the app's own pairing, API client and call controller against a running dev copy of the backend (`DevCopyTest`). One `CallController` owns the state of the one call there can be; the notification, the screens and the services only show that state and report taps to it. How it is built, installed and set up on a phone is in `parent-app/README.md`; every decision with its reason is in `docs/superpowers/plans/2026-11-15-parent-app-2-android-app.md`. The ones that shape the rest:

- **Ringing is a notification, not a service** – a call-style notification with a full-screen intent, on a channel whose sound is the phone's ringtone. It is the only way Android lets an app in the background show a ringing screen. Two consequences: the ring follows the phone's own sound setting (as the design asks), and on the small banner that shows while the phone is in use Android writes the two buttons itself («Svar» / «Avslå»); the full ringing screen says «Svar» / «Ikke nå».
- **No Telecom integration** (`androidx.core:core-telecom`). It would take the audio routing away from LiveKit, and nothing in the design needs it.
- **Push registration by Firebase installation id** (`FirebaseMessaging.register()`, `onRegistered`), not the token API that Google deprecated in June 2026. If pushes should not arrive that way, one class changes (`push/FirebasePushAddress.kt`). The build script reads Firebase's values out of the operator's `google-services.json` itself; Google's Gradle plugin is not used, and without the file the app builds and says it cannot be rung.
- **`targetSdk` 36, not 37.** The phone keeps its access to the home network without a new permission prompt, and the app stays clear of Android 17's stricter rule for sound started from the background.
- **Test builds are a second app.** `debug` and `minified` install as «Menkerud Home (test)» and may be paired with any server (the dev copy); a release build accepts a QR code for `https://call.noobventure.com` only, so nobody can talk a parent into pairing with a foreign server.
- **What Android does to an app in the background is planned for.** The push service does not return before the notification is up; «decline» on the notification holds on until the server has been told; a call that ends after Android restarted the app still takes its ringing notification away; a call whose other side has been gone for ten seconds, or never shows up within thirty, ends by itself.
- **While a call is on, the screen turns with the phone.** The kiosk's picture is 16:9; upright it is a band across the screen, turned it fills it.

What is still unproven is everything a PC cannot stand in for – that the phone rings (also locked, also on mobile data), a call with picture and sound, the call living on in the background, the shrunk build: the written run on a real phone is Task 11 of that plan, and it needs the operator's Firebase project and a phone on a cable.

**Reviewed on 2026-11-16 by a fresh reviewer, before the phone run; one fix pass.** It found no certain crash and no certain failure to ring. What was fixed: **(1)** A phone could lose its pairing for good through a passing failure of the Android Keystore – and the server, which still listed the phone and could still push to it, would have kept sending calls to an app that could not answer them, with no Discord link either (the one thing the changeover must never do). Now the keystore is asked three times, the pairing file is deleted only when it can definitely never be opened, a 401 unpairs only in the API's own words (`{"error":"unauthorized"}`, not a proxy's), and a phone that does lose its pairing by itself leaves the push service, so that the server's next push bounces and the server stops counting it as paired (`pairing/PairingLoss.kt`). **(2)** A phone whose clock was a second behind the server's rang for 45 s while home rang for 60; it now rings for the minute. **(3)** The home screen could say «Klar» with the «Anrop hjemmefra» notifications turned down, with the app shut out of the background, or while the server did not know where to push; each is now named. **(4)** The banner carries «Det ringer hjemmefra»; a room that cannot be made, or will not close, ends the call instead of the app; and the phone's log says what happened to a push. The plan's note on going back to push tokens was wrong by one step and is corrected. What was not fixed is in §10.

**The backend in production is unchanged until part 3.** The container on Unraid still runs the September code. The kiosk gets its side of part 1 with the next «Hent oppdatering»; against the old backend that changes nothing on the screen – the stream request gets a 404 and is asked again quietly, at most once a minute – apart from tidier endings when a call cannot be set up (§3.10). A fresh reviewer went through the whole branch on 2026-11-15; what it found that mattered was fixed the same day (a failed start could hold the line until a restart; a parent could ring into nothing; a call hung up before the API had answered rang on; the kiosk's new routes were open on a server without a device key; a proxy's 404 counted as an empty room) and the API contract in the plan was corrected before the app is written against it. Still to come: part 2, the Android app (`parent-app/`); part 3, the rollout; and, once both parents use the app, removing the answer page and the Discord link.

**For the rollout (part 3) – the list so far:** `ADMIN_PASSWORD` (long and random: the pairing page has no limit on wrong guesses) · host port 3009 published on the LAN address only (`192.168.68.74:3009:3001`), never through SWAG · the appdata volume mounted (after a rebuild the pairing page must still list the phones) · the Firebase key file · `DEVICE_KEY` set – without one the kiosk's stream and its answer routes are refused · SWAG and Cloudflare must not buffer or cut the event stream: hold it open for ten minutes and watch the keep-alives · both test suites run once on Node 20 (`node:20-alpine`; they were written and run on Node 24) · `/healthz` shows `livekitAdmin: true` from inside the container · the Task 0 test (one call answered on mobile data, Wi-Fi off) · from the app's review: the two *part 3* findings in §10 · two phones for one parent ringing at once has never been tried · the shrunk build must be built again with the Firebase file and tried before a release build goes on a phone.

**Done ahead of the rollout – the kiosk's Chrome may make sound on a page nobody has touched (2026-11-15).** Chrome keeps a page silent until somebody has touched it: Web Audio stays `suspended`, `<audio>` is blocked and speech is refused (`not-allowed`). The kiosk had neither a flag nor a policy against that, so after a restart or a reload – until the first touch – an incoming call would have shown «… ringer!» without the ring tone and without the voice, and a new Beskjed arrived without its chime (an older gap; it matters more once parents ring home from the app). The launcher `~/.local/bin/menkerud-home.sh` now carries `--autoplay-policy=no-user-gesture-required` (DEPLOYMENT.md, which also says how to restart Chrome without logging out), and Chrome was restarted with it. Tried first with the kiosk's own Chrome 153 – a second, headless one on a throw-away profile: as it comes, all three are refused; with the flag all three work. After the restart the page was alive again (it spoke to the screen helper, Home Assistant and Discord). Not yet seen: the kiosk's own page ringing untouched – that waits for the first call from the app.

**Known limits of what is built:** removing a phone on the pairing page does not end a call that phone is in (its ticket for that one room lasts ten minutes at most); a parent who rings home at night wakes the screen and rings, like any incoming call; a phone that is switched off still counts as paired, so a call to it is silent – the Discord link comes back only when the push service reports the address dead. The reviewer's smaller findings, none of them fixed, are the last item of §10.
